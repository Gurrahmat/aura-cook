Redux Toolkit, explained through your own app

The state layer of AuraCook was rewritten today: KitchenContext.jsx is gone, and a Redux store took its place. This page explains what that means, in plain language, using only code you now own.

The one-sentence idea. Redux is a single object that holds all the shared data in your app, plus a strict rule for changing it: you never edit the object directly, you send a message describing what happened, and a plain function decides how the object changes. Every screen that cares reads its slice of that object.

1Why we changed anything

The old version used Context. It worked, but it had a real flaw you can now explain:

  • The provider held pantry, timers, page state and toasts in one object.
  • Whenever any part of that object changed, every component that read the context re-rendered.
  • Your timers tick once per second. So the pantry table, the toasts, the navbar — everything — re-rendered once per second even though nothing about them had changed.

With Redux, each component says exactly which value it wants. If that value didn't change, the component does not re-render. That single difference is the whole reason for the migration.

Say this in the viva "We started on Context API. It worked, but the provider's value object was recreated on every render and our timer ticks every second, so every consumer re-rendered once a second — including the pantry table, which doesn't read timers. We moved to Redux Toolkit so each component subscribes with useSelector to just the slice it needs."

2The five words you must know

WordPlain meaningIn your app
Store The single object holding all shared data. src/store/store.js — one store with three sections.
Slice One section of that object, with its own rules for changing it. pantry (the stock), timers, ui (page, drawer, toasts).
Action A message: "this happened". A plain object with a type and a payload. { type: 'pantry/itemAdded', payload: {...} }
Reducer A pure function: given the old state and an action, return the new state. The four functions inside pantrySlice.
Dispatch / Selector Dispatch = send an action. Selector = read a value out. dispatch(itemAdded(fields)) · useSelector(selectPantryItems)
The cycle, memorise it: component → dispatch(action) → reducer computes new state → store notifies → components whose selected value changed re-render.

3Your store, file by file

src/store/ ├── store.js configureStore + listener middleware + saves the pantry ├── pantrySlice.js the stock: add, update, delete, restore staples ├── timerSlice.js the timers: add, pause/resume, reset, delete, tick ├── uiSlice.js current page, active recipe, drawer open, toasts ├── selectors.js read helpers + memoised (cached) calculations └── hooks.js useAppDispatch / useAppSelector src/utils/ ├── match.js computeRecipeMatch(recipe, pantry) ← plain function └── sound.js playTimerBell() src/components/TimerEngine.jsx renders nothing; dispatches tick() every second

Why utils/ is separate: computeRecipeMatch is maths, not state. Keeping it as a pure function means the selector can cache it and you can test it without React.

4A reducer, line by line

This is the real code from pantrySlice.js, simplified:

// a slice = a section of the store
const pantrySlice = createSlice({
  name: 'pantry',                       // actions become 'pantry/itemAdded'
  initialState: { items: loadPantry() }, // read from localStorage once
  reducers: {
    itemAdded: {
      reducer(state, action) {
        state.items.push(action.payload);   // looks like a mutation...
      },
      prepare(item) {                       // ...but prepare ran first
        return { payload: normalize({ ...item, id: `p_${Date.now()}` }) };
      }
    },
    itemDeleted(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload.id);
    }
  }
});
  • state.items.push(...) is not a real mutation. RTK wraps the state in a draft (using a library called Immer); your push is recorded and a new immutable array is produced. That's why reducers can look normal while still respecting "never mutate state".
  • prepare runs before the reducer. It's where we generate the id and clamp the quantity. Why? Because a reducer must be a pure function — same input, same output. Generating a random id or reading the clock inside a reducer would break that.
  • The invariant lives here, not in the form: normalize() forces quantity ≥ 0 and sets "Out of Stock" when it hits 0. So even if someone dispatches itemAdded from the console with -5, the rule still holds.
Quiz: why can't the reducer play the timer bell?

Because a reducer must have no side effects — no audio, no network, no timers. If it did, React's development double-invocation (StrictMode) could ring the bell twice. Side effects go in listener middleware, which runs after the reducer.

5Reading state: useSelector

const toasts = useAppSelector(selectToasts);          // ToastContainer
const currentPage = useAppSelector(selectCurrentPage);  // App.jsx / Navbar
const timerCount = useAppSelector(selectTimerCount);    // the navbar badge

Each of those subscribes to one value. The toast layer does not re-render when a timer ticks, because it never asked for timers.

The clever bit: cached calculations

// selectors.js — a factory, so every card gets its OWN cache
export const makeSelectRecipeMatch = () =>
  createSelector(
    [(state, recipe) => recipe, selectPantryItems],
    (recipe, pantry) => computeRecipeMatch(recipe, pantry)
  );

// RecipeCard.jsx
const selectMatch = useMemo(() => makeSelectRecipeMatch(), []);
const match = useAppSelector(state => selectMatch(state, recipe));

createSelector remembers the last inputs it saw and returns the cached result when they haven't changed. The factory matters: a shared selector has only one cache slot, so six cards would keep evicting each other. Each card making its own gives six independent one-slot caches.

If they ask "what is memoisation?" "Remembering the result of a calculation and reusing it while the inputs stay the same. Our match percentage is recomputed only when that recipe or the pantry changes — not on every keystroke, and not on every timer tick."

6Changing state: dispatch

From PantryPage.jsx, the submit handler ends with one line:

if (editItem) {
  dispatch(itemUpdated({ id: editItem.id, fields }));
} else {
  dispatch(itemAdded(fields));
}
setShowModal(false);   // local UI state stays local

Two things to notice, and both are viva answers:

  • The component does not build the id or clamp the number or decide the status — the reducer does. The component just reports what the user did.
  • The modal open/closed flag is still local useState. Not everything belongs in Redux. Rule: shared or long-lived → store; one screen and temporary → useState.

7Side effects: listener middleware

Some things must happen in response to a change but are not state: ringing the bell, showing a toast, saving to localStorage. Those live in store.js:

listenerMiddleware.startListening({
  actionCreator: timersTicked,               // "when a tick happens..."
  effect: (action, api) => {
    const { timers } = api.getState().timers;   // read the NEW state
    timers
      .filter(t => t.status === 'finished' && !t.notified)
      .forEach(timer => {
        playTimerBell();
        api.dispatch(timerNotified(timer.id));   // so it fires once
        api.dispatch(toastAdded(`⏰ "${timer.name}" done!`, 'warning'));
      });
  }
});

And the toast queue cleans itself up the same way: a listener waits 4 seconds, then dispatches toastRemoved.

This is the line that scores marks: "Reducers stay pure; every side effect — the bell, the toast timeouts and persistence — lives in listener middleware." It shows you know where things belong, not just that they work.

8Saving the pantry

// store.js — a store is not a component, so there is no useEffect
let lastPantryItems = store.getState().pantry.items;

store.subscribe(() => {
  const items = store.getState().pantry.items;
  if (items !== lastPantryItems) {      // only when it really changed
    lastPantryItems = items;
    savePantry(items);                   // localStorage.setItem(JSON)
  }
});

Reading happens once, in the slice's initialState: { items: loadPantry() }; writing happens on every change. The reference check matters: without it, the one-second timer tick would write to localStorage every second.

9What you can now answer that others can't

QuestionYour answer in one line
Why Redux over Context?Narrow subscriptions — only components reading the changed slice re-render.
What's a slice?One section of the store with its own reducers; `createSlice` generates the actions and the reducer together.
Why does `state.items.push` work?Immer — it records the change on a draft and produces an immutable copy.
Why `prepare`?To build the payload (ids, clamping) before the reducer, keeping the reducer pure.
Where do side effects go?Listener middleware, never a reducer.
What's `createSelector` for?Memoisation — recompute the match percentage only when recipe or pantry changes.
Is everything in Redux now?No. The search box, filters, open modal, step index and form fields are local `useState`.
How do you debug it?Redux DevTools: every action with its payload, and the state before/after.
Prove it to yourself in 60 seconds (no laptop needed) Say out loud, in order: "The user submits the pantry form → the component dispatches itemAdded → prepare adds the id and clamps the quantity → the reducer appends to state.items → Immer makes a new array → the store tells its subscribers → the table, the recommendations and the recipe badges re-render → the listener shows a toast → subscribe saves it to localStorage." That is the entire state layer of your project.

10The live coding task they love

If they hand you a pen, it will be "write a slice". Practise this until it takes four minutes:

import { createSlice, nanoid } from '@reduxjs/toolkit';

const todosSlice = createSlice({
  name: 'todos',
  initialState: { items: [] },
  reducers: {
    todoAdded: {
      reducer(state, action) { state.items.push(action.payload); },
      prepare(text) { return { payload: { id: nanoid(), text, done: false } }; }
    },
    todoToggled(state, action) {
      const t = state.items.find(i => i.id === action.payload);
      if (t) t.done = !t.done;
    },
    todoRemoved(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload);
    }
  }
});

export const { todoAdded, todoToggled, todoRemoved } = todosSlice.actions;
export default todosSlice.reducer;

// store.js
export const store = configureStore({ reducer: { todos: todosReducer } });

// main.jsx:  <Provider store={store}><App /></Provider>
// component: const items = useSelector(s => s.todos.items);
//            const dispatch = useDispatch(); dispatch(todoAdded('buy milk'));

Then expect the follow-up: "how would you fetch todos from an API?" → createAsyncThunk, which creates three actions automatically (pending, fulfilled, rejected) that you handle in extraReducers to set status and error, and the UI renders a skeleton, an error card with Retry, or the list.
